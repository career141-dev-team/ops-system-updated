# Page two: the deployment, and every key it asks for

Written 6 November 2026, after page one ([26](26-RUN-IT-FOR-REAL.md)), which
is the laptop running the real system. This page takes that and puts it on a
server.

[22](22-GO-LIVE.md) is the *order* — the server once, backups, every switch
off, one switch a day, the pilot, which sheet stops when. It is right and this
page does not repeat it. This page is the thing 22 never had: **every key,
every account, every permission, in one list, with where each one goes and who
it has to be asked for.**

One correction to 22 before anything else: its section 3 says the first deploy
runs with *"`OPS_DEV_SIGNIN=off` with Clerk as the door"*. **Clerk is not
built.** No authentication package is installed; `src/lib/session.ts` is the
pick-a-name development sign-in and nothing else. With `OPS_DEV_SIGNIN=off`
the app does not run at all — every page redirects to a sign-in that cannot
sign anybody in. Section 1.1 of page one is therefore a prerequisite of this
whole page, not a detail of it.

## 2. Every key, in one table

Four columns: what it is, where you get it, where it is set, and what breaks
without it. **None of these values ever goes in the repository, a commit, a
document or a chat message.**

### 2.1 The ones you generate yourself

`openssl rand -hex 32` each. No account, no cost, nobody to ask.

| Key | Set on | Without it |
|---|---|---|
| `OPS_CLOCK_KEY` | the app **and** the Ops Convex deployment (the same value on both) | no clock runs: no chase, no reminder, no guarantee warning, no Monday report |
| `OPS_API_TOKEN` / `OPS_TA_TOKEN` | the same string on the **TA** deployment and on **Ops** | the link stays shut at 401 and Ops runs on recorded sample data |
| `OPS_WEB_LEAD_KEY` | the app, and given to whoever looks after the website | the website form cannot post a lead |
| `OPS_SESSION_SECRET` | the app | nothing today — it is read by no code. It becomes real with sign-in |
| The Convex **instance secret** | the backend container | the backend will not start |
| The Convex **admin key** | generated by the backend, then set as `CONVEX_SELF_HOSTED_ADMIN_KEY` | the app cannot read or write its own database |
| The Postgres password for `convex_ops` | the backend container | the same |
| A password hash for the preview's Caddy block | the Caddy config | the test-data preview is open to the internet |

### 2.2 Microsoft 365 — email, in and out

Asked for once, from your Microsoft 365 admin. This is the longest lead time
on the page; start it first.

| Thing | Where it is set | Without it |
|---|---|---|
| `MS_TENANT_ID` | the app | no mail at all |
| `MS_CLIENT_ID` | the app | — an app registration for **Ops**, not the TA System's |
| `MS_CLIENT_SECRET` | the app | — and note its expiry date somewhere you will see it |
| **`Mail.Read`**, application, admin-consented | the app registration | no reply is ever read; the desk goes back to Outlook |
| **`Mail.Send`**, application, admin-consented | the app registration | every approved message records as *blocked* instead of going |
| **An application access policy** | the tenant | without one, those two permissions reach **every mailbox in the company**, not only ours. Ask for a policy restricting the app to a group holding exactly the boxes below |
| ~~`ops@career141.com`~~ | **Not needed (6 Nov)** | Every message goes from the person's own address, never a shared one. Point `OPS_COMMON_MAILBOX` at `opsteam@`, which already exists and is already read, and create nothing |
| `OPS_MAILBOXES` | the app | nothing is polled |
| `OPS_COMMON_MAILBOX` | the app | a client thread is one person's alone |

The boxes: `ops@`, `opsteam@`, `joborders@`, `cv@`, `interviews@`, `hello@`,
and each ops person's own address. Nobody changes how they work — the reader
reads the box the reply actually landed in.

## 3. The one thing on this page that could really hurt

`convex deploy` **replaces every function on the deployment it points at.**
That is how the live TA backend was overwritten from a laptop on 21 September.

The protections, and all three must hold:

1. Ops has **its own deployment** on its own ports. The TA System's is a
   different address.
2. `convex deploy` runs **only inside the deploy workflow**, on the server,
   against `127.0.0.1`. Never from a laptop. `AGENTS.md` hard rule 1, and this
   session's own rules refuse it.
3. All Ops backend code lives in **this** repository under `convex/ops/`. A
   second repository deploying to the same backend would wipe the first one's
   functions.

## 4. The switch order, corrected

[22](22-GO-LIVE.md) section 4 has the order and the daily pace. Use it, with
two changes:

| Day | Switch | Changed how |
|---|---|---|
| 1 | `OPS_MAIL_READ=on` | unchanged |
| 2 | `OPS_TA_READS_ENABLED=on`, `OPS_TA_FAKE=off` | unchanged |
| 3 | `OPS_TA_WRITES_ENABLED=on` **and** `switch.taWritesEnabled` in Settings, **and** `OPS_API_WRITES_ENABLED=on` + `OPS_API_ACTOR_EMAIL` on the TA side | 22 named only the first two. All four are needed, and the last two are on the **other** system |
| 4 | `OPS_SEND=on`, the lock on and holding the pilot client's addresses | unchanged |
| later | the lock off | **22 said to set `OPS_OUTREACH_LIVE=on` here. Do not, until it is a switch that does something.** Taking the lock off is the real step, and it is the one that needs the most thought |

Every one is reversible in under a minute, and nothing is lost while one is
off: clocks keep their dates, writes stay queued, messages record as *blocked*
rather than failed.

## 6. The pilot, and how it ends

One client. Two weeks. Their addresses in the allow-list and nobody else's.
Every message still drafted and approved by a person — that never changes,
pilot or not.

Each day: the Health screen (mail runs per box, the events cursor age, the
outbox, the clocks), and the audit for anything a person did by hand that the
system should have done. **What the team works around is the list of what to
fix** — not a complaint, the most valuable output of the two weeks.

Then the review: what was sent, what TA received, what was bypassed. Fixes
first. Then the allow-list comes off, one client at a time, not all at once.

## 8. When a thing goes wrong

`docs/runbooks/` holds seven, written with phase 8: the restore, the outage,
the stuck outbox, the mail reader, the TA link, the clocks, and the one for a
message that went to the wrong person. The Health screen is the first place to
look and says what it last heard from each part.

The order to read them in is whatever the Health screen points at. If it
points at nothing and something is still wrong, it is the sign-in or the
database, in that order.
