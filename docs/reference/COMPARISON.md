# Ops final flow vs the TA System: common points, gaps and permissions (27 Oct 2026)

How this was made: the final Ops flow (c3626 locked business flow, c5237 latest system flow, dated decisions) was compared stage by stage, from **client onboarding to close**, with the TA System code on main (`4c355c4`) and the feature skills. Every "TA System today" cell is checked in code (file named) unless marked *(skill)* (taken from the repo feature skills) or *(unverified)*. Status: **SAME** = already works for this step; **EXTEND** = the object/screen exists, behaviour is missing; **NEW** = nothing exists.

## 0. Result in one paragraph
The two systems share one spine: **client -> opening -> team seats -> candidate application stages -> Director round -> client round -> interview -> offer -> placement -> fee/guarantee**, plus the same alert bell, mailboxes, safety gates and sign-in. Ops owns the steps *before* the opening (lead, ESA, requirement) and *after* the placement (invoice, guarantee, close), and the client-facing parts in between. About a third of what the Ops canvas calls "missing" **already exists in the TA System** (interview scheduling, ESA records, placement terms, joining-date alerts); a few items are **dormant or broken** (ESA has no screen, Place goes to a page that does not exist); and the real **new** work is the lead/ESA workflow, client communication, invites/Teams, money and the timers.

## 2. Common points (what is really shared)
1. **Clients** (`clients`, `/clients`): the one master record. Ops creates and owns it; TAs read it. Today the edit right (`client.manage`) excludes `ops`.
2. **Openings** (`jobs`, `/openings`): created by Ops from the requirement, worked by the TA. Fields the Ops plan needs already exist: JD, salary, location, requirements, priority P1-P5 and day-N-of-target, status, work locations, `clientId`.
3. **Team and mode** (`jobAssignments`, `workingStage`, `taLeadId`): the Ops "assign TA, daily 100%" step is the same object.
4. **The stage ladder** (`applications.currentStage`, translator `convex/ta/stages.ts`): Director Review -> Director Shortlist -> Client Shortlist -> Interview -> Offer -> Placed are exactly the hand-over steps in c5237. The `client` role already sees only the last four.
5. **Review rounds** (`reviewRounds`): Director round works; the client round is the same table and is the one that is "held".
6. **Interviews, offers, placements, ESA** (`interviews`, `offers`, `placements`, `esaRecords`): all exist; the money chain `esaRecords -> placements (fee %, guarantee days snapshot) -> closing checklist` is already wired for placements.
7. **Alerts and bell** (`src/lib/sla.ts`, `notifications`, `taAlerts`, NotificationBell): the LINK notices in c5237 ("owner alerted", "TA alerted of booking", "Asma and ops told") use this channel.
8. **Mail and WhatsApp** (Graph mailboxes joborders@, shortlists@, interviews@, opsteam@; Meta Cloud API) and the **outbound safety gates** (`outreachSafety.ts`, `outboundGuard.ts`, `OUTREACH_LIVE` off by default).
9. **Sign-in and roles** (Clerk -> `users.taRole`; `ops` already exists and is desk-wide).
10. **Reports and Master Sheet** (`commercial.manage`), **Bin** (7-day restore for clients/openings), **`activityLog`** (audit of Master Sheet edits).

## 3. Permissions: what exists, what Ops needs
Today there are **20 capabilities** in `src/lib/auth.ts` (`can()`; default is "no"; `viewer` read-only; deactivated users refused). Desk-wide roles (never narrowed to one opening): admin, director, ta_lead, ops.
| Capability | Who has it today | Ops flow use | Change |
|---|---|---|---|
| `client.manage` (create/edit/delete clients, contacts) | admin, director, ta_lead | ops owner creates and maintains clients | **add `ops`** (or a new `ops_lead`/`ops_owner`) |
| `commercial.manage` (fees, guarantees, fall-throughs, ESA, Master Sheet) | admin, director, ta_lead, ops | ESA, invoices, payments, guarantee | keep; **split** into `esa.manage`, `finance.manage`, `guarantee.refund` so accounts (Asma) and the Director of Operations get only what they need |
| `opening.create` / `opening.manage` / `opening.act` / `opening.read` / `opening.sourcing` | everyone except client / desk-wide + seats | requirement -> opening; interviews; offers; placement | ops already desk-wide; add rule: ops owner of the client may act on that client's openings only if ops should be narrowed (Q on scope: "does ops see all clients or only theirs" from the canvas decisions) |
| `decide.director` / `decide.client` | admin, director, ta_lead (+ assigned contact, + via recorded reply) | Director Review, client decisions | ops stays out (decision: Director/client processes unchanged) |
| `interview.feedback` | desk-wide or any assignment | client interviewer feedback | keep |
| `report.read`, `database.read` | everyone except client | weekly report | keep; add scheduled report |
| `user.manage` | admin | add ops people, roles | keep |
| `intake.handle` | everyone except client | unfiled CVs | keep |
| `strategy.*`, `voice.practice`, `link.note`, `review.note` | (TA features) | none | keep |
New capabilities the plan needs: `lead.manage`, `esa.manage`, `client.comms.approve` (approve every client/Director email), `interview.schedule`, `finance.manage`, `guarantee.refund`, `ads.marketing`. New roles only if people need them: `ops_lead`, `accounts`, `marketing`, `director_ops`.
Rules that interact with Ops: the **TA collision lock** (first TA to shortlist owns the candidate) does not apply to desk-wide roles, so ops can act on any candidate; the **workday gate** applies to TAs only; `client` and `viewer` are never allowed to act; backend functions under `convex/ta/*` are internal and re-check access with `assertJobAccess` (ops users are desk-wide there too, via `isDeskWideUser`).
